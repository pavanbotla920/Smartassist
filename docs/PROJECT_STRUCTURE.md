## 1. Top-Level Directory Overview

The repository is organized into distinct functional layers separating Django configuration, business logic, static assets, templates, internationalization, and deployment files:

| Directory / File | Description & Purpose |
| :--- | :--- |
| `smartassist/` | The root Django project configuration package (settings, root URLs, WSGI, ASGI). |
| `farmers/` | The core Django application containing models, views, forms, business logic, and signals. |
| `templates/` | Global HTML templates for user interfaces, dashboard screens, and partial components. |
| `static/` | Static front-end assets including custom stylesheets, JavaScript modules, images, and GeoJSON. |
| `locale/` | Multilingual translation catalogs (`.po` and `.mo` files) supporting 19+ Indian languages. |
| `data/` | Directory designated for raw datasets, supplementary records, or data imports. |
| `docs/` | Project documentation, architectural standards, and team guidelines. |
| `venv/` | Local Python virtual environment (**never committed**; ignored by `.gitignore`). |
| `Dockerfile` | Container configuration for building and running the project across environments. |
| `.dockerignore` | Defines files excluded from the Docker build context. |
| `requirements.txt` | Python package dependencies pinned for reproducibility. |
| `manage.py` | Django command-line execution entry point. |
| `schemes.csv` | Primary seed dataset of central and state government agricultural schemes. |
| `schemes_data.csv` | Secondary/backup CSV dataset of agricultural schemes. |
| `setup_i18n.py` | Automation script for initializing and compiling translation catalogs. |
| `db.sqlite3` | Local development SQLite database (**local only; never commit or overwrite**). |

## 2. Django Configuration Package (`smartassist/`)

The `smartassist/` folder is generated by Django as the central control room for the entire project.

```text
smartassist/
├── __init__.py         # Marks this directory as a Python package
├── asgi.py             # ASGI entry point for asynchronous servers (e.g., streaming chatbot)
├── settings.py         # Global configuration (apps, middleware, databases, i18n, auth)
├── urls.py             # Root URL routing table with multilingual i18n patterns
└── wsgi.py             # WSGI entry point for traditional synchronous web servers (e.g., Gunicorn)
```

### Key Responsibilities
- **`settings.py`**:
  - `INSTALLED_APPS`: Registers core Django apps plus our custom `'farmers'` app.
  - `MIDDLEWARE`: Manages session tracking, security headers, CSRF verification, and `LocaleMiddleware` for automated language switching.
  - `TEMPLATES`: Configured to find templates in the top-level `templates/` directory.
  - `DATABASES`: Configured by default for local SQLite (`BASE_DIR / 'db.sqlite3'`).
  - `LANGUAGES` & `LOCALE_PATHS`: Configures English, Hindi, Marathi, Telugu, and others, mapping to `BASE_DIR / 'locale'`.
  - `STATIC_URL` & `STATICFILES_DIRS`: Maps `/static/` to the root `static/` folder.
  - `EMAIL_*`: SMTP settings for sending account and application notifications (e.g., Gmail integration via environment variables).
  - `OPENAI_API_KEY`: Reads the AI assistant API key from system environment variables.
- **`urls.py`**:
  - Defines admin routes (`admin/`) and language selection endpoint (`i18n/setlang/`).
  - Uses `i18n_patterns` with `prefix_default_language=False` so URLs cleanly support localized routes (e.g., `/hi/schemes/`, `/te/schemes/`) while keeping default English unprefixed (`/schemes/`).
  - Maps citizen endpoints, volunteer/admin dashboards, chatbot endpoints, speech synthesis, and analytics APIs.
- **`wsgi.py` & `asgi.py`**:
  - `wsgi.py` is used by standard HTTP servers like Gunicorn.
  - `asgi.py` enables asynchronous HTTP handling, essential for streaming responses from the AI chatbot and edge-tts endpoints.

## 3. Core Application Package (`farmers/`)

The `farmers/` folder is our primary Django application containing the domain logic for farmers, schemes, applications, and support roles.

```text
farmers/
├── __init__.py         # Python package marker
├── admin.py            # Django Admin registration and dashboard customizers
├── apps.py             # Application configuration and signal wiring
├── forms.py            # Django forms for authentication, citizen profile, and scheme applications
├── load_data.py        # Database loader script to import schemes from schemes.csv
├── models.py           # Database entities (Scheme, UserProfile, ApplicationRequest, Notification)
├── signals.py          # Event listeners (e.g., automatically creating UserProfile upon User creation)
├── tests.py            # Automated tests for models, views, and business workflows
├── views.py            # View controllers for pages, APIs, search, voice, and chatbot
├── data/
│   └── farmer_schemes_dataset.csv   # App-specific scheme dataset
└── migrations/
    ├── 0001_initial.py
    ├── ...
    └── 0008_update_rkvy_official_website.py
```

### Key Components

1. **`models.py`**:
   - `UserProfile`: Extends Django's `User` with role-based access (`citizen`, `volunteer`, `admin`), mobile number, state, district, age, income range, category (SC/ST/OBC/General), and education.
   - `Scheme`: Stores central and state agricultural schemes, eligibility parameters (min/max age, income limits, education, category), benefits, official website, and application links.
   - `ApplicationRequest`: Tracks assistance requests submitted by citizens or filed by volunteers, with a lifecycle status (`Submitted` &rarr; `Under Review` &rarr; `Applied` &rarr; `Approved` / `Rejected`).
   - `Notification`: Records outgoing email or SMS alerts dispatched to users.

2. **`views.py`**:
   - **Citizen Views**: `home`, `scheme_awareness` (catalog), `scheme_detail`, `apply_for_assistance`, `application_status`, `my_applications`, `recommend_schemes`.
   - **Admin / Volunteer Views**: `admin_dashboard`, `manage_schemes`, `update_application_status`, `apply_scheme_admin`, `reports`.
   - **Multilingual & Voice Services**: `set_language`, `scheme_translation_api`, `scheme_voice_audio` (audio playback using `edge-tts`).
   - **AI Chatbot & Speech**: `chatbot`, `chatbot_stream` (Server-Sent Events for OpenAI or fallback rule-based bot), `transcribe_voice`.
   - **Geographic & State APIs**: `india_map_overview_api`, `india_map_state_analytics_api`, `schemes_by_state_api`, `state_schemes_public_api`.

3. **`signals.py`**:
   - Listens to `post_save` on `User` to automatically instantiate an attached `UserProfile`.

4. **`load_data.py`**:
   - A standalone runner (`python manage.py shell` or script) that reads `schemes.csv` and populates the `Scheme` table with defaults and metadata.

## 4. Templates, Static Assets, Translations, Datasets & Migrations

### 4.1 Templates (`templates/`)
Templates use Django's template engine with Bootstrap 5 and custom CSS. All user-facing strings are wrapped with `{% trans %}` or `{% blocktrans %}` for internationalization.

- **Layout & Shared**:
  - `base.html`: Common HTML shell, navigation bar, Bootstrap imports, and footer.
  - `partials/language_selector.html`: Reusable dropdown component for switching languages.
- **Citizen Features**:
  - `home.html`: Homepage banner and quick entry points.
  - `scheme_awareness.html`: Instant search, filter chips, and interactive cards for all schemes.
  - `scheme_detail.html`: Detailed scheme breakdown, text-to-speech player, and interactive Leaflet map.
  - `apply.html` & `application_status.html`: Application submission and tracking.
  - `recommend.html`: Question-driven scheme recommendation interface.
  - `india_map_schemes.html` & `interactive_india_map.html`: Geographic scheme visualization across Indian states.
  - `state_dashboard.html`: State-filtered view of agricultural schemes.
- **Authentication**:
  - `login.html`, `register.html`, `profile.html`.
  - `password_reset.html`, `password_reset_done.html`, `password_reset_confirm.html`, `password_reset_complete.html`.
- **Administrative**:
  - `admin_dashboard.html`: Application triage and status review for staff/volunteers.
  - `reports.html`: Aggregated statistics on applications, scheme coverage, and demographics.

### 4.2 Static Assets (`static/`)
- `static/css/`:
  - `scheme-platform.css`: Core design system, badges, layout grids, cards, modals, and responsive styling.
  - `language-switcher.css`: Styling for the interactive language selector dropdown.
- `static/js/`:
  - `scheme-platform.js`: Modal dialogs, client-side filtering, and application actions.
  - `language-switcher.js`: Handles language selection change events and cookie updates.
  - `scheme-localization.js`: Asynchronous in-browser scheme card translation.
  - `scheme-voice.js`: Speech playback trigger connecting to the backend TTS audio API.
- `static/images/`: Government emblem, banners, and farmer showcase photography.
- `static/india_states.geojson`: Vector boundary polygons of Indian states used by Leaflet maps.

### 4.3 Translations (`locale/`)
- We support 19+ Indian languages (Assamese, Bengali, Bodo, Gujarati, Hindi, Kannada, Konkani, Malayalam, Manipuri, Marathi, Nepali, Odia, Punjabi, Sanskrit, Santali, Sindhi, Tamil, Telugu, Urdu).
- Each directory follows `locale/<lang_code>/LC_MESSAGES/django.po` (editable source) and `django.mo` (compiled binary).
- Run `python setup_i18n.py` or `python manage.py compilemessages` whenever translations are updated.

### 4.4 Datasets
- `schemes.csv` (Root): Master CSV file containing verified central and state schemes.
- `farmers/data/farmer_schemes_dataset.csv`: Dataset copy packaged with the farmers app.
- `data/`: Dedicated location for incoming or raw state agricultural datasets.

### 4.5 Database Migrations (`farmers/migrations/`)
- Database schema changes are tracked sequentially (from `0001_initial.py` through `0008_update_rkvy_official_website.py`).
- Always run `python manage.py makemigrations` and `python manage.py migrate` when updating models.
- **Do not manually edit past migration files**; generate new migration files instead.

## 5. Future Architecture & Feature Placement

As the platform grows, keeping code organized prevents `views.py` and `models.py` from becoming overcrowded. Team members must place future features according to the following architectural guide:

```text
farmers/
├── api/                     # 1. Dedicated API Layer (DRF or Django Ninja)
│   ├── __init__.py
│   ├── serializers.py      # Serializers for Scheme, ApplicationRequest, UserProfile
│   └── views.py            # API ViewSets and endpoints
├── services/                # 2. Business Logic & External Integrations
│   ├── __init__.py
│   ├── recommendations.py  # Recommendation algorithms & scoring logic
│   ├── chatbot.py          # LLM prompts, RAG pipeline, context retrieval
│   ├── speech.py           # TTS synthesis (Edge-TTS) & STT transcription
│   ├── analytics.py        # Aggregations, metric computation, report generation
│   └── notifications.py    # SMS gateways, WhatsApp APIs, email dispatch
└── tasks/                   # 3. Asynchronous Background Tasks (Celery / Redis)
    ├── __init__.py
    └── notifications.py    # Async email and SMS queue processing
```

### Specific Feature Guidance

1. **Recommendation Engine**:
   - **Current Location**: `recommend_schemes` and `_find_matching_schemes` in `farmers/views.py`.
   - **Future Location**: Extract algorithmic and machine-learning recommendation logic into `farmers/services/recommendations.py`. When ready for machine learning models (scikit-learn / PyTorch), store model artifacts in `data/models/` and call inference from `farmers/services/recommendations.py`.

2. **Chatbot & Speech Services**:
   - **Current Location**: Functions in `farmers/views.py` (`chatbot`, `chatbot_stream`, `_stream_edge_speech`).
   - **Future Location**: Place LLM orchestration, conversation memory, and prompt templates in `farmers/services/chatbot.py`. Move voice synthesis and transcription to `farmers/services/speech.py`.

3. **Analytics & Reporting**:
   - **Current Location**: Direct ORM counts inside `reports()` and `india_map_*` views.
   - **Future Location**: Place aggregation logic, data warehousing queries, and export utilities (CSV/PDF) inside `farmers/services/analytics.py`.

4. **REST APIs**:
   - **Current Location**: Custom `JsonResponse` endpoints in `farmers/views.py`.
   - **Future Location**: Group all API routes under `farmers/api/` with structured schemas, token authentication, and pagination.

5. **Notification Services**:
   - **Current Location**: `Notification` model and direct SMTP calls.
   - **Future Location**: Centralize SMS (e.g. CDAC / MSG91 / Twilio) and email dispatch in `farmers/services/notifications.py`. Use background task runners (such as Celery) for non-blocking sends.

## 6. Docker & DevOps Configuration

### Current Files
- **`Dockerfile`**:
  - Base Image: `python:3.12-slim` for minimal container size and security.
  - Working Directory: `/app`.
  - Installs requirements without caching: `pip install --no-cache-dir -r requirements.txt`.
  - Runs database migrations followed by `python manage.py runserver 0.0.0.0:8000`.
- **`.dockerignore`**:
  - Excludes `.git`, `venv/`, `__pycache__/`, `*.sqlite3`, and `.env` files to prevent bloated or insecure container images.

### Running with Docker Locally
```bash
# 1. Build the Docker image
docker build -t smartassist-kisan .

# 2. Run the container
docker run -p 8000:8000 smartassist-kisan
```

### DevOps Guidelines for Production
1. **WSGI Server**: Replace `runserver` in production with a production-grade application server such as **Gunicorn** or **Uvicorn** (for ASGI).
2. **Database**: Swap SQLite for a managed **PostgreSQL** instance in production by setting the `DATABASE_URL` environment variable.
3. **Environment Secrets**: Never bake credentials into Docker images. Pass `SECRET_KEY`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, and `OPENAI_API_KEY` via `.env` files or container orchestration secrets (Docker Compose, Kubernetes, or AWS ECS).
4. **Static Files**: Run `python manage.py collectstatic --noinput` during container build or deployment, and serve static assets via Nginx or a CDN.

## 7. Naming Conventions

Consistency keeps our codebase readable. Follow these conventions across all contributions:

### 7.1 Python (PEP 8)
- **Files & Modules**: `snake_case.py` (e.g., `load_data.py`, `recommendations.py`).
- **Classes**: `PascalCase` (e.g., `Scheme`, `UserProfile`, `ApplicationRequestForm`).
- **Functions & Methods**: `snake_case()` (e.g., `get_eligible_schemes()`, `apply_for_assistance()`).
- **Variables & Attributes**: `snake_case` (e.g., `scheme_name`, `is_authenticated`).
- **Constants**: `UPPER_SNAKE_CASE` (e.g., `STATUS_CHOICES`, `DEFAULT_FROM_EMAIL`).

### 7.2 HTML & Templates
- **Template Files**: `snake_case.html` (e.g., `scheme_awareness.html`, `admin_dashboard.html`).
- **Partial Templates**: Prefix with an underscore or place in `partials/` (e.g., `partials/language_selector.html`).
- **Element IDs**: `kebab-case` (e.g., `id="sp-sort-select"`, `id="login-prompt-title"`).
- **CSS Classes**: `kebab-case` with component prefixes (e.g., `.sp-card-body`, `.sp-badge-central`).

### 7.3 Static Files (JavaScript & CSS)
- **Filenames**: `kebab-case.js` and `kebab-case.css` (e.g., `scheme-platform.js`, `language-switcher.css`).
- **JavaScript Functions & Variables**: `camelCase` (e.g., `playSchemeSpeech()`, `cardsContainer`).

### 7.4 Git Branch Names
Format: `<type>/<short-description>` using lower-case and hyphens:
- `feature/recommendation-engine`
- `feature/voice-search-hindi`
- `bugfix/translation-key-mismatch`
- `hotfix/login-redirect-loop`
- `docs/project-structure`
- `refactor/extract-notification-service`

## 8. Git Workflow & Collaboration Guidelines

To keep the `main` branch stable, all team members must follow this feature-branch workflow.

### 8.1 Branching Workflow

```text
[origin/main] ───────┬───────────────────────────────────► [PR Merged]
                     │                                         ▲
                     ▼                                         │
              [git checkout -b feature/...] ──► [Commit] ──► [Push]
```

1. **Always start from the latest `main` branch**:
   ```bash
   git checkout main
   git pull origin main
   ```
2. **Create your feature branch**:
   ```bash
   git checkout -b feature/your-feature-name
   ```
3. **Write code and test locally**:
   - Activate your virtual environment: `source venv/bin/activate`
   - Run system checks: `python manage.py check`
   - Run unit tests: `python manage.py test`
4. **Stage only the relevant files**:
   ```bash
   git add farmers/views.py templates/scheme_detail.html
   ```
5. **Commit with clear, descriptive messages**:
   ```bash
   git commit -m "Add speech synthesis playback to scheme detail page"
   ```
6. **Push to your remote branch**:
   ```bash
   git push origin feature/your-feature-name
   ```

### 8.2 Strict Rules for All Team Members

> [!CAUTION]
> **NEVER Commit Local SQLite Databases**
> `db.sqlite3` contains local data and must **never** be staged (`git add db.sqlite3`), committed, or overwritten in pull requests. Keep database updates managed purely through migration files (`makemigrations`).

> [!IMPORTANT]
> **Pre-Push Validation Checklist**
> Before pushing your branch, always run:
> 1. `python manage.py check` &rarr; Ensure 0 issues found.
> 2. `git diff --check` &rarr; Ensure no leftover conflict markers or syntax errors.
> 3. `git status` &rarr; Ensure no unintended files (such as `.env`, `.pyc`, or `db.sqlite3`) are staged.

### 8.3 Submitting a Pull Request (PR)

1. Open a Pull Request from `feature/your-feature-name` into `main`.
2. Provide a clear PR description:
   - **What changed**: Summary of features added or bugs resolved.
   - **Why**: The problem being solved or user story addressed.
   - **How to test**: Step-by-step instructions for the reviewer to verify the behavior locally.
   - **Screenshots**: If the PR alters user-facing templates.
3. Every PR requires at least **one peer review approval** from a team member before merging.
4. **Resolving Merge Conflicts**:
   - Rebase or merge `main` into your feature branch:
     ```bash
     git checkout feature/your-feature-name
     git fetch origin
     git merge origin/main
     ```
   - Resolve conflicts in your editor, test thoroughly, remove all conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`), stage the files, and conclude the merge commit.
   - Never use `git reset --hard` or overwrite teammates' work blindly.
